# 이슈 기반 작업 절차

기존 Claude `/work`의 의도를 에이전트 공통 절차로 옮긴 문서다. 슬래시 명령이나 특정 `Agent` 도구가 있어야 실행되는 절차가 아니다. 입력은 Linear 이슈 번호 또는 작업 설명이다.

## 1. 이슈 확인

- 변경 작업 전 [Linear 규칙](linear.md)을 읽고 프로젝트 필터를 적용해 이슈를 확인한다.
- 설명만 주어지면 승인 범위를 확인한다. 이슈 생성까지 승인되었으면 중복 확인 후 생성한다. 이슈가 없으면 변경을 시작하지 않는다. 추가 생성 승인이 필요할 때만 구체적인 초안을 제시한다.
- 변경 작업 시작 시 이슈를 In Progress로 전환한다.

## 2. 별도 워크트리에서 구현

- 문서·설정을 포함한 변경 작업은 [Git 규칙](git.md)에 따라 별도 워크트리를 사용한다. 이미 지정된 워크트리가 있으면 이어서 사용한다. 새 작업은 기본적으로 `dev`에서 분기하되 사용자 지정 기준을 우선한다. 원래 작업 디렉토리에서 브랜치를 전환하지 않는다.
- 브랜치명은 Git 규칙을 따른다. 실제 이슈 번호를 반드시 포함한다.
- 사용자가 위임을 요청했거나 적용 지침에서 요구한 경우, 지원되는 에이전트 도구로 위임하고 워크트리 경로·이슈 번호·제목·설명·작업 범위를 전달한다. 그 외에는 담당 에이전트가 워크트리에서 직접 수행한다.
- 코드를 구현하고 루트 AGENTS.md의 완료 기준에 따라 변경에 필요한 검증을 수행한다. 코드 변경에는 관련 테스트, 타입·런타임 변경에는 타입 검사와 빌드를 포함한다. 실패하면 원인을 확인하고 수정 후 재검증한다.
- 커밋이 요청 범위에 있을 때만 관련 파일을 `rtk git add <파일>`로 스테이징한다. `git add -A`는 사용하지 않는다.
- 커밋이 요청 범위에 있으면 `[ALGOGO-{번호}] {type}: {한글 설명}` 형식을 사용한다.

## 3. PR과 완료

- 요청에서 승인된 범위에 따라 기능 브랜치를 push하고 `dev` 대상 PR을 생성한다. 본문은 [Git 규칙](git.md)의 템플릿을 따른다.
- PR 생성 시 연결된 Linear 이슈의 상태를 In Review로 바꾼다. 승인된 머지를 셀프 리뷰 직후 수행한다면 원래 규칙에 따라 생략할 수 있다.
- 리뷰와 테스트를 확인한 뒤 승인된 범위에서 squash merge하고 기능 브랜치를 삭제한다.
- 실제 머지 완료 후에만 연결된 Linear 이슈를 Done으로 바꾸고 이슈 결과에 PR 링크를 기록한다.
- 구현·검증 결과와 미완료 항목을 한글로 보고한다.

대안을 비교하고 선택한 결정이 있으면 ADR 작성 필요성을 확인한다. 코드만으로 드러나지 않는 이유는 ADR에 기록한다.
