# TypeScript / NestJS 구현 기준

적용 대상: `src/**/*.ts`, `test/**/*.ts`, `tsconfig*.json`, `eslint.config.mjs`.

## 변경 범위와 판단

- 타입 안전성, 외부 계약, 데이터 무결성을 우선한다. 요청을 해결하는 가장 단순한 설계를 선택한다.
- 기존 코드는 작업에 필요한 범위만 수정한다. 파일명·스타일 통일이나 일반 규칙 적용을 위한 일괄 정리는 섞지 않는다.
- 실제 설정과 인접 코드를 확인한다. 이 문서로 라이브러리 버전이나 설정의 존재를 추정하지 않는다.

## 타입과 계약

- `strict`를 유지한다. `any`, 무분별한 타입 단언, 검사 억제로 오류를 숨기지 않는다. 외부의 불확실한 값은 `unknown`에서 검증하고 좁힌다.
- DTO·파라미터·반환 타입 변경 시 입력 → 변환 → 사용처를 추적한다. DB 스키마, API/소켓 계약, 가드·인터셉터, 주요 호출부의 일관성을 확인한다. 확인하지 못한 외부 계약은 추정으로 바꾸지 않는다.
- 추론이 명확하면 타입을 반복하지 않는다. 공개 서비스 계약에는 반환 타입을 명시하고, 유효한 상태를 유니온·판별 필드로 표현한다.
- 단언보다 타입 선언·타입 가드·`satisfies`를 우선한다. `as const`, 테스트 mock, Prisma의 문자열을 검증된 도메인 타입으로 바꾸는 경계에서는 근거 있는 단언을 허용한다.
- 신규 상수 집합은 `as const` 객체를 기본으로 한다. 기존 enum을 단순 스타일 정리 목적으로 바꾸지 않는다.
- 타입만 사용하는 import는 `import type`을 사용한다. Nest 의존성 주입 토큰이나 런타임 데코레이터 메타데이터에 필요한 클래스는 값으로 import한다.

## 계층과 모듈

- Controller/Gateway는 전송 계층, Service는 비즈니스 로직·트랜잭션 경계, Repository는 데이터 접근을 담당한다. 역방향 의존을 만들지 않는다.
- 도메인별 모듈을 유지한다. 외부 모듈은 export된 Service를 통해 접근하고 Repository를 직접 노출하지 않는다.
- 생성자 주입과 `private readonly`를 기본으로 한다. DI 대상 서비스를 직접 생성하지 않는다.
- 순환 의존을 새로 만들지 않는다. 공통 책임 추출이나 이벤트로 해소하고, `forwardRef()`로 설계 문제를 덮지 않는다.
- Repository는 없는 단건 데이터에 `null`을 반환하고, Service가 도메인 예외를 결정한다. DB 오류를 없는 데이터로 바꾸거나 삼키지 않는다.
- `common/`에는 여러 도메인에서 실제로 공유하는 안정적인 책임만 둔다.

## 입력·응답·예외

- HTTP와 소켓 입력은 DTO와 `class-validator`로 경계에서 검증한다. `whitelist`가 필요한 필드를 제거하지 않는지 확인한다.
- 숫자·배열 등 변환은 `class-transformer`로 명시한다. 타입 선언이나 Swagger 데코레이터만으로 런타임 검증을 대신하지 않는다.
- 필수 DTO 필드의 런타임 주입에는 `!`, 선택 필드에는 `?`, 기본값에는 초기화를 사용한다. 응답 DTO는 필요한 필드만 노출하고 Swagger 계약을 유지한다.
- 도메인 오류는 기존 `CustomHttpException` 계층과 필터의 응답 계약을 따른다. 코드는 `DOMAIN_ACTION`, 메시지는 한글, 예외 클래스 파일명은 기존 PascalCase 규칙을 따른다.
- Service에서 비즈니스 예외를, Guard/Pipe에서 인증·검증 예외를 처리한다. 소켓 오류는 해당 예외 필터와 ACK 계약을 확인한다.
- 오류의 원인을 보존한다. 로깅 책임을 한 경계에 두어 같은 오류를 중복 기록하지 않는다. catch 후 재던질 때는 상위에서의 처리까지 고려한다.

## 데이터와 비동기 자원

- Repository에서 PrismaService를 사용한다. 필요한 필드는 `select`로 제한하고 불필요한 추상화 계층을 추가하지 않는다.
- Raw SQL은 파라미터화된 `Prisma.sql`을 사용한다. 사용자 입력을 문자열 보간해 `$queryRawUnsafe`에 전달하지 않는다.
- 원자성이 필요한 쓰기는 트랜잭션으로 묶는다. 기존 `@Transaction()`을 사용할 때 실제 클라이언트 교체와 중첩 동작을 확인한다.
- `async/await`를 기본으로 한다. try/catch에서 비동기 실패를 처리하려면 `await`한다. Promise 조합이나 명시적인 비동기 오류 처리에 필요한 `.then()`/`.catch()`를 금지하지 않는다.
- 독립 작업은 병렬 실행한다. 부분 실패를 허용할지에 따라 `Promise.all`과 `Promise.allSettled`를 선택한다. 순서가 필요한 쓰기는 직렬로 처리한다.
- 큐·Redis 구독·소켓·타이머를 만든 주체가 정상 종료, 실패, 연결 해제에서 정리한다. 타임아웃과 재시도는 중복 처리·취소·멱등성까지 고려한다.
- BullMQ 작업 추가는 Service가 담당한다. Gateway에 실행 비즈니스 로직을 넣지 않는다.

## 저장소 관례

- 신규 일반 파일과 DTO는 kebab-case, 클래스는 PascalCase, 변수·메서드는 camelCase, 상수는 UPPER_SNAKE_CASE를 따른다. 도메인 예외는 기존 PascalCase를 유지한다.
- 상대 경로로 직접 import하며 새 barrel 파일이나 path alias를 도입하지 않는다.
- 매개변수가 여러 개이고 의미 구분이 필요하면 객체 매개변수를 사용한다. 단순한 기존 호출부를 기계적으로 바꾸지 않는다.
- `const`와 불변 데이터를 기본으로 하고, 성능이나 명확한 소유권이 있는 지역 연산에는 변경 가능한 자료구조를 허용한다.
- 린트·포맷 설정에 이미 있는 문법 규칙은 설정을 따른다. 코드로 명확한 내용을 주석이나 별도 문서로 반복하지 않는다. TODO에는 작성자와 해결할 내용을 기록한다.

## 설정·로그·보안

- 애플리케이션 설정은 `src/config/`와 ConfigModule을 사용한다. 환경 변수 추가 시 검증 스키마도 갱신한다. bootstrap/config와 별도 실행 스크립트는 해당 환경의 주입 방식을 따른다.
- 현재 브랜치의 `src/logger/`에서 제공하는 AppLogger와 DI 구성을 사용한다. 특정 로깅 패키지를 문서만 보고 추가하지 않는다.
- 로그에는 원인 파악에 필요한 구조화된 맥락을 포함한다. 운영 개입이 필요한 실패는 error, 복구 가능한 이상은 warn, 주요 상태 변경은 info/log, 개발 진단은 debug를 사용한다.
- 비밀번호·토큰·API 키를 로그에 남기지 않고 운영 응답에 스택을 노출하지 않는다.
- 인증은 기존 AuthGuard/WsAuthGuard, 역할 검증은 RolesGuard와 `@Roles()`를 따른다. 새 경로에서 메서드·클래스 메타데이터의 실제 적용을 확인한다.

## 검증

- 버그는 가능하면 수정 전 실패를 재현하고 수정 후 통과하는 회귀 테스트를 추가한다. 테스트는 구현 문구나 mock 호출만이 아닌 관찰 가능한 계약을 검증한다.
- 신규 Service의 비즈니스 로직은 단위 테스트한다. 변경된 로직에는 정상·경계·실패 경로 중 관련된 경우를 포함한다. 테스트 설명은 한글로 작성한다.
- 단위 테스트는 직접 의존성만 필요한 만큼 mock한다. DB 검색·트랜잭션, S3 객체 처리, 큐/소켓 수명주기는 실제 로컬 서비스 통합 검증을 추가한다.
- 타입·데코레이터·빌드 설정 변경은 타입 검사와 빌드를 확인한다. Jest의 변환 성공만을 전체 타입 검사로 간주하지 않는다.
- 테스트는 독립적으로 실행 가능하게 하고 자신이 만든 데이터와 자원을 정리한다. 기존 실패와 신규 회귀를 구분하되, 근거 없이 기존 문제라고 단정하지 않는다.
